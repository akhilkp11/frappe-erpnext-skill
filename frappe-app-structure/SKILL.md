# Custom app structure and delivery

## Rule of thumb
All customization lives in a custom app under Git. Nothing in `apps/frappe` or `apps/erpnext` is edited (a temporary diagnostic patch is fine, but never committed or left on a production bench). One app per deployable concern; do not create an app per client unless the code really differs, otherwise use settings/DocTypes to vary behavior.

## Layout (after `bench new-app my_app`)
```
apps/my_app/
  pyproject.toml            # build metadata; dependencies; python requirement
  my_app/
    hooks.py                # all registrations
    modules.txt             # one module name per line (must match module folders)
    patches.txt             # [pre_model_sync] / [post_model_sync]
    my_module/doctype/<name>/{<name>.json,<name>.py,<name>.js,test_<name>.py}
    my_module/report/<name>/...
    public/js, public/css   # included via app_include_js / doctype_js
    templates/, www/        # portal pages and Jinja
    fixtures/               # generated by export-fixtures
    setup/install.py        # after_install helpers
```
Verify the exact scaffold your bench generates (v15 and v16 differ in packaging details) rather than copying paths from memory.

## hooks.py essentials
`required_apps` (dependency + install order), `app_include_js/css`, `doctype_js`, `doc_events`, `scheduler_events`, `fixtures`, `after_install`, `after_migrate`, `override_*`. Keep handler code in modules, not inline. Anything you add to `after_migrate` must be idempotent because it runs on every migrate.

## Environment and versions
- v16 targets newer Python/Node/MariaDB than v15 (see `frappe-devops`); one app can support both only if its dependencies and syntax allow it. Decide a policy: branches `version-15` and `version-16` (or `develop` mapped to the newest), cherry-pick between them, and pin `bench get-app --branch`.
- Declare dependencies in `pyproject.toml`; installing an app on a bench runs the requirements step, so keep them minimal and pinned to compatible ranges.

## Quality gates
- `pre-commit` with formatters/linters (ruff/black-style for Python, prettier/eslint for JS) so diffs stay reviewable.
- Tests under each DocType and module; run with `bench --site test_site run-tests --app my_app` (see `frappe-testing-debugging`).
- CI: GitHub Actions that start MariaDB/Redis, init a bench for the target branch, install ERPNext (and dependencies like HRMS/India Compliance if needed), install the app, run tests. Mirror the workflow that Frappe's own apps publish for your target branch instead of inventing one.
- Run `frappe-code-review/scripts/frappe_lint.py` in CI for cheap guardrails.

## Release and deploy
Tag releases; deploy by updating the app branch on each bench, then migrate and build. On Frappe Cloud, the app is added to a Bench Group from a GitHub repo and deployed from the dashboard; keep the repo clean (no secrets, no committed `node_modules`, valid `pyproject.toml`, correct `required_apps`).

## Splitting apps
Move code between apps only with patches that fix `module` references on DocTypes, Custom Fields, Reports and Print Formats; test on a copy of production data. Moving a DocType between apps is risky; prefer deprecating and migrating data.
